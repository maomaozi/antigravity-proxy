# 账号专属的一次性聊天：设计方案

## 目标与边界

- Google 和 Codex 两个账号池的每行操作区增加“聊天”按钮，打开独立聊天页，并在页首持续显示账号、提供商和当前模型。
- “一次性”指一次打开页面期间可以连续多轮对话；刷新、关闭页面或点击“新对话”后，消息和附件立即从页面状态中移除。没有历史列表、恢复入口或分享链接。
- 请求始终使用入口所选的账号。账号过期、额度不足、冷却或上游失败时显示错误，不自动换号。模型只能选对应提供商已配置的模型。
- 服务器不存储聊天内容或附件，不创建上传文件。账号凭据和现有账号健康状态仍由现有机制管理。

## 页面与交互

账号列表操作区：`[聊天] [重置/删除] [展开]`。按钮有文字和 `aria-label`，点击不触发行展开。账号不可用时仍可进入页面查看原因，但发送按钮禁用并展示状态。

聊天页建议使用 `/frontend/chat.html?provider=google|codex&account=<编码后的邮箱>`。URL 只放账号标识，不放凭据、模型消息或附件。页面加载时从现有账号接口确认账号存在、可用，并获取对应模型列表；账号被删除或不可用时禁用发送。

```
桌面（>= 768px）
┌────────────────────────────────────────────────────────────┐
│ ← 账号池   一次性聊天     Google · user@example.com  [新对话] │
│ 模型 [下拉选择]                       页面关闭后对话即消失   │
├────────────────────────────────────────────────────────────┤
│                    消息区域（独立滚动）                     │
├────────────────────────────────────────────────────────────┤
│ [图片/文件]  已选附件标签及移除按钮                          │
│ [输入消息，Enter 发送 / Shift+Enter 换行]           [发送]  │
└────────────────────────────────────────────────────────────┘

手机（< 768px）
┌──────────────────────────────┐
│ ← 聊天       [新对话]         │
│ Google · user@example.com    │
│ [模型选择，整行宽度]          │
├──────────────────────────────┤
│ 消息区域                     │
├──────────────────────────────┤

```

页面高度用 `100dvh`，顶部与输入区固定、消息区滚动；底部留出安全区，避免手机虚拟键盘遮挡。账号邮箱允许换行或省略并可查看完整值，触控按钮至少 44×44 px。空状态提示“一次性对话，关闭页面后无法恢复”。发送时显示流式回复和“停止生成”；中断后保留已收到的文本，并可继续发送。切换模型时开始新对话，避免把不同模型的上下文混在一起。回复按纯文本展示，或使用安全的 Markdown 渲染，绝不把模型输出直接写入 `innerHTML`。页面进入浏览器后退缓存后也应清空旧对话。

## 附件处理

首版明确支持 PNG/JPEG/WebP 图片，以及 UTF-8 文本类文件（TXT、MD、CSV、JSON、常见源码）、PDF 和 DOCX。图片在浏览器内按需缩小后转为 data URL；文本文件用 `File.text()` 读取；PDF 和 DOCX 在浏览器用本地打包的解析器提取文本。扫描版 PDF 若无可提取文本，提示用户改用图片。其他格式在选择时说明不支持，不上传到服务器。

发送前按文件数量、单文件大小、总请求大小和提取后的字符数进行限制；服务端再次校验 MIME、data URL、请求字节数和文本长度。默认建议：单文件 5 MiB、单次最多 5 个附件、总原始附件 10 MiB、提取文本最多 100,000 字符；最终阈值还需与上游模型可接受的请求大小对齐。附件在发送后仅以本轮上下文保存在浏览器内，后续轮次为保持语境会随消息历史再次发送；待发送附件可在界面移除，已发送附件可用“新对话”清空。整个消息历史也设置请求体上限，达到时提示开始新对话，避免多轮重复发送大附件导致内存及网络用量持续增长。浏览器不写 `localStorage`、`sessionStorage`、IndexedDB 或 Cache API。

文本附件转换为带文件名、类型及明确边界的用户消息文本；图片使用现有 Google `image_url` / Codex `input_image` 的 base64 输入通路。PDF 和 DOCX 仅发送提取出的文本，不发送原始二进制。文件名作显示和引用用途，须转义；不作为服务器路径。上传和解析全在浏览器内完成，服务器不需要独立上传接口或临时目录。

## 请求接口与账号固定

新增 `POST /api/ephemeral-chat`，请求体示例：

```json
{
  "provider": "google",
  "accountEmail": "user@example.com",
  "model": "antigravity-gemini-3.8-flash",
  "messages": [
    { "role": "user", "content": [
      { "type": "text", "text": "请概括附件" },
      { "type": "image", "url": "data:image/png;base64,..." }
    ] }
  ]
}
```

服务端重新查询账号池并核对提供商、模型、账号状态和内容限制；不能信任浏览器传来的账号状态。新接口只接受同源浏览器请求，并沿用部署环境对管理页面的访问控制；当前服务没有独立的后台登录机制，因此部署时需继续限制管理页面及 API 的访问。以统一 SSE 事件返回 `text_delta`、`usage`、`error` 和 `done`，便于两个提供商共用同一个聊天 UI。请求断开或点击停止时，通过 `AbortSignal` 取消上游请求。

Google 路径复用现有消息适配、模型转换和流式解析，但给 `executeCompletion` 增加仅限此接口使用的严格账号选择参数：取指定账号、按现有规则刷新令牌、检查模型能力与冷却，然后只用该账号和允许的上游连接重试。不能通过现有 session binding 或 `getBestAccount` 的自动轮换来模拟账号固定。

Codex 路径复用现有 Responses 代理和 SSE 解析，但同样增加严格账号参数；现有 `preferredEmail` 只是偏好，选择失败后会轮换，不能直接用于此功能。保持上游会话 ID 在本页多轮请求期间一致（由浏览器持有随机 ID，服务端只校验并转发），不用数据库会话绑定。若上游需要完整上下文，每轮从浏览器发送当前消息列表。Codex 上传图片应按其当前实际可接受的输入结构验证；若所选模型或上游拒绝图片，返回清晰的“不支持图片输入”错误。

## 数据生命周期与空间占用

| 数据 | 保存位置 | 生命周期 |
| --- | --- | --- |
| 消息、附件原始内容与预览 | 当前浏览器页面内存 | 新对话、刷新或关闭页面即清除 |
| 请求体与流式响应 | 服务器/网络临时内存 | 请求结束或取消后释放 |
| 账号凭据与健康状态 | 现有账号存储 | 保持现有机制 |

现有 Google 和 Codex 代理会向 SQLite 写 session binding 及逐请求 token usage。一次性聊天路径需要显式跳过这两类写入，并避免把正文、附件 data URL 或模型回复写入日志；页面仅临时显示本轮用量。健康状态、令牌刷新和必要的冷却更新仍沿用账号池逻辑。这样聊天功能不会增加随使用次数增长的磁盘内容。注意服务提供方仍会接收实际发送的数据；“一次性”只描述本代理与浏览器的保存行为。

## 验收重点

1. 两个账号池的每一行均可进入聊天；实际请求始终命中所点账号，账号不可用时不轮换。
2. 多轮文本、图片与受支持文件能完成对话；不支持格式、超限及上游拒绝时给出可理解的错误。
3. 停止、网络中断、刷新和新对话均不会残留附件或聊天记录；服务器无上传临时文件、聊天记录和该功能的 session/usage 数据库记录。
4. 在桌面、窄屏手机、软键盘弹出和深浅色模式下，输入框、附件及发送按钮始终可用；键盘与屏幕阅读器可操作。
5. 限制请求体并验证输入，模型输出安全渲染，账号 ID 不暴露凭据。

## 建议实现顺序

先完成严格账号固定与不持久化的后端接口，再做独立聊天页和两处入口，最后接入浏览器内附件解析与响应式校验。使用现有单元测试验证账号固定和数据不落盘，再进行两种提供商的手工多轮与移动端检查。
